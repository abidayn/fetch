# Operations

How to run, deploy, release, and maintain Fetch. Commands assume Git Bash on
Windows unless marked PowerShell. Architecture and code conventions are in
`CLAUDE.md`; the reasons behind these choices are in `decisions.md`.

> **Dev and production share one database.** A backend running on your laptop,
> and every backfill script, reads and writes **production data**. The Gemini
> free-tier quota (20 classifications/day) is also shared between laptop and server.

---

## 1. Local development

```bash
# backend (from backend/)
python -m venv venv && venv/Scripts/python.exe -m pip install -r requirements.txt
cp .env.example .env        # fill in GEMINI_API_KEY, DATABASE_URL, JWT_SECRET_KEY
venv/Scripts/python.exe -m uvicorn main:app --reload        # http://127.0.0.1:8000/docs

# mobile (from mobile/)
flutter pub get
flutter run                                                  # emulator → http://10.0.2.2:8000
flutter run --dart-define=API_BASE_URL=https://fetch-production-35a4.up.railway.app
```

A physical phone can't reach `10.0.2.2`; point it at the production URL (or your
laptop's LAN IP) with `--dart-define`.

## 2. Backend deployment (Railway)

**Production:** `https://fetch-production-35a4.up.railway.app` — Railway,
Southeast Asia (Singapore) region, built from `backend/Dockerfile`.

### How a deploy happens

Railway builds from the GitHub repo's `main` branch. After merging, **always
verify** production actually runs the new code — a stale deploy once made the
app call endpoints the server didn't have:

```bash
curl -s https://fetch-production-35a4.up.railway.app/health        # {"status":"ok"}
curl -s https://fetch-production-35a4.up.railway.app/openapi.json | grep -o '"/[a-z/{}_]*"' | sort -u
```

The route list should match `backend/routers/`. If it's stale, trigger
**Redeploy** on the latest deployment in the Railway dashboard.

### Service settings (already configured — for rebuilding from scratch)

| Setting | Value | Note |
|---|---|---|
| Root Directory | `backend` | Without it Railway can't find the Dockerfile and the first build fails with an auto-detect error. |
| Variables | `GEMINI_API_KEY`, `DATABASE_URL`, `JWT_SECRET_KEY`, `GROQ_API_KEY` (optional last-resort fallback); optionally `CLASSIFY_MODELS` / `ANSWER_MODELS` to change the fallback chains | No quotes, no surrounding spaces. Railway stages variable changes — click **Deploy** to apply them. Use a production-only `JWT_SECRET_KEY` (`python -c "import secrets; print(secrets.token_urlsafe(48))"`); changing it logs everyone out. |
| `DATABASE_URL` | Supabase **session pooler** URL (`aws-0-ap-southeast-1.pooler.supabase.com`) | The direct `db.<ref>.supabase.co` host is IPv6-only. |
| Networking | **Generate Domain** | Railway doesn't create a public URL by default. |
| Region | Southeast Asia (Singapore) | Same region as the database. Response header `x-railway-edge: sin1` confirms it. |
| Serverless | **On** | Sleeps after ~5 min idle; otherwise it runs 24/7 and burns the credit. First request after sleep may return a 502 (the app retries once). |

The container listens on `$PORT` (see the Dockerfile `CMD`) and runs a single
uvicorn worker.

### Logs

Open the active deployment in the Railway dashboard → its runtime log.
Useful searches:

| Log line | Meaning |
|---|---|
| `item <id> enriched: platform=… sources=[…] ai=True embedding=True` | A save was fully processed. `sources` shows which extraction path worked. |
| `yt-dlp failed for …` | YouTube blocked yt-dlp from Railway's IP; the oEmbed fallback should still get the title. |
| `llm classify: served_by=<model>` / `llm answer: served_by=<model>` | Which model answered. Anything but the chain's first model means a fallback kicked in. |
| `llm classify: gemini:… -> quota_exhausted` | That model's daily quota is gone (shared with the laptop); it's skipped until midnight Pacific. Fallback models take over; nothing to do. |
| `llm … -> unavailable` / `-> rate_limited` | Overload, timeout or per-minute limit; the chain retried or moved on. |
| `llm …: every model in the chain failed` | All models failed (e.g. every quota gone). Classification is retried by the upgrade job later. |
| `upgrade: item … re-classified (<old> -> <primary>)` | The upgrade job replaced a fallback-written (or failed) summary with the primary's. |
| `… -> unusable` | A model name no longer exists or a key was rejected: fix `CLASSIFY_MODELS` / `ANSWER_MODELS` or the key. |

### Database migrations

Migrations are **not** run on deploy. Because dev and prod share the database,
run them from the laptop (from `backend/`):

```bash
venv/Scripts/python.exe -m alembic current          # should print the head revision
venv/Scripts/python.exe -m alembic upgrade head
```

Deploy code that *needs* a new column only after the migration has run.
Always read autogenerated migrations before applying them (see "Gotchas" in `CLAUDE.md`).

## 3. Maintenance scripts (from `backend/`)

| Command | When |
|---|---|
| `venv/Scripts/python.exe backfill_enrichment.py` | Items stuck unprocessed or whose Gemini call failed (e.g. after a quota day). |
| `… backfill_enrichment.py --ids <uuid> …` | Re-process specific items from scratch (re-scrape + re-classify), e.g. after an extraction fix. Clears user edits on those items. |
| `… backfill_enrichment.py --reclassify` | Re-run classification on every item's stored `raw_content` without re-scraping — after a prompt/model change. Uses the full fallback chain; items done by fallback models get upgraded later. Overwrites user edits. **Gentler:** set `classified_by = NULL` on the items to redo and let the automatic upgrade job work through them within the primary's spare quota. |
| `… backfill_embeddings.py` | Items with a summary but no embedding. |
| `… backfill_embeddings.py --all` | **Required** after changing the embedding model or dimensions (plus a migration if the dimension changes). |
| `check_db.py`, `check_gemini.py` | Quick connectivity checks for `DATABASE_URL` / `GEMINI_API_KEY`. |

These run against the shared production database.

## 4. Releasing the Android app

GitHub Actions (`.github/workflows/android-release.yml`) builds a signed
release APK whenever a tag starting with `v` is pushed, and attaches it to a
GitHub Release. Normal commits don't trigger it.

```text
push tag v0.7.1
  → GitHub runner: check the 5 settings exist → install Java + Flutter
  → decode the keystore from a secret → flutter build apk --release
    (--dart-define=API_BASE_URL=<production>, --build-number=<run number>)
  → GitHub Release "v0.7.1" with app-release.apk
```

### Releasing a new version

```bash
git checkout main && git pull
git tag v0.7.1            # always a new, higher number
git push origin v0.7.1
```

Watch the run under the repo's **Actions** tab (≈ 5–10 min). If the release
depends on backend changes, deploy and verify the backend (§2) **first**.

The build number comes from the workflow run number, so each APK can install
over the previous one. The visible version name stays `1.0.0` (from
`pubspec.yaml`) regardless of the tag.

### The signing key

Android only installs an **update** if it's signed with the **same key** as
the installed app. One permanent release key exists:

| | |
|---|---|
| Keystore | `C:\Users\Acer\fetch-release.jks` (outside the repo) |
| Alias | `fetch` |
| Certificate SHA-256 | `f305f924…8062030` (as read from the released APK) |
| Password | one password, used for both the store and the key |

**Back up the keystore file and its password** (e.g. a password manager). Lose
either and future updates can't install over existing installs — everyone
would have to uninstall and reinstall.

Check you still know the password (PowerShell):

```powershell
keytool -list -keystore "$HOME\fetch-release.jks"
```

> `C:\Users\Acer\fetch-signing\` holds an **older, unused** keystore (different
> certificate) with its password in a plain-text file. Nothing is signed with
> it. Delete that folder once you've confirmed the key above is backed up.

### GitHub settings the workflow needs

Repo **Settings → Secrets and variables → Actions**:

| Name | Type | Value |
|---|---|---|
| `ANDROID_KEYSTORE_BASE64` | secret | the keystore file, base64-encoded |
| `KEYSTORE_PASSWORD` | secret | the keystore password |
| `KEY_PASSWORD` | secret | the same password |
| `KEY_ALIAS` | secret | `fetch` |
| `API_BASE_URL` | variable | `https://fetch-production-35a4.up.railway.app` |

To set or rotate them (PowerShell, from the repo; the password prompts keep it
out of your shell history):

```powershell
[Convert]::ToBase64String([IO.File]::ReadAllBytes("$HOME\fetch-release.jks")) | gh secret set ANDROID_KEYSTORE_BASE64
gh secret set KEYSTORE_PASSWORD
gh secret set KEY_PASSWORD
gh secret set KEY_ALIAS --body fetch
gh variable set API_BASE_URL --body https://fetch-production-35a4.up.railway.app
```

### When a build fails

Open the red run in **Actions** and read the first error line.

| Message | Fix |
|---|---|
| `X is not set in the repo settings` | Add setting `X` (table above). |
| `Keystore was tampered with, or password was incorrect` | Wrong `KEYSTORE_PASSWORD`. |
| `Cannot recover key` | Wrong `KEY_PASSWORD` (must equal the keystore password). |

Re-run a failed build without a new tag: `gh run rerun <run-id>`.

## 5. Installing on a phone

1. **First install only:** uninstall any Fetch built on a laptop — it's signed
   with a debug key, and Android refuses to update across keys ("App not
   installed"). Items live on the server; you only log in again.
2. Open in the phone's browser (always the newest release):
   `https://github.com/abidayn/fetch/releases/latest/download/app-release.apk`
3. Open the download → allow **Install unknown apps** for the browser → **Install**.
4. **Play Protect** says it hasn't seen an app from this developer: tap
   **More details → Install anyway**. It's a warning about the new signing key,
   not a finding about the app. If there's no install option at all, install
   over USB instead: enable **Developer options → USB debugging**, plug in, and
   run `adb install app-release.apk`.

Later releases install over the existing app with no uninstall.
